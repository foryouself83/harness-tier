# LLM Wiki (임베딩 미사용) 설계

- 날짜: 2026-08-06
- 브랜치: `feature/llm-wiki`
- 티어: DEV (gates: precommit · review · doc-sync)

## 배경과 목표

개발 지식(코드·설계·ADR·장애·개선 이력)을 임베딩/RAG 없이 관리한다. 문서는 사람이 읽는
Markdown 본문 + 기계가 읽는 YAML Front Matter로 구성하고, Front Matter를 기계적으로 파싱해
Knowledge Graph(`graph.yaml`)를 생성한다. LLM은 문서 작성과 `related` 추천까지만 담당하고,
graph 생성과 검증은 일반 코드가 담당한다.

검색 recall은 임베딩 대신 두 단계로 확보한다: 본문 전문 검색(BM25 등)으로 진입점 문서를
찾고, 거기서 graph를 넓혀 주변 문서를 끌어온다. `aliases` 필드가 유사어 격차를 메운다.

확장 깊이는 **고정 hop 수가 아니라 컨텍스트 예산에 종속**된다. 순환은 visited 집합으로
막히므로 제약이 되지 못한다. 실제 제약은 분기다 — 분기 계수 4에서 3 hop이면 60여 개 문서,
300줄 문서 환산 200k 토큰이라 예산이 먼저 터진다. 지식 그래프는 small-world라 3~4 hop이면
사실상 전체에 닿고, 그것은 wiki를 통째로 로드하는 것과 같아 graph를 둘 이유를 없앤다.
graph의 가치는 무엇을 가져올지가 아니라 무엇을 **안** 가져올지 정하는 데 있다. 따라서
확장기는 hop 순서로 넓히되 예산에 닿으면 중단하고, edge를 `depends_on` → `related` 순으로
따라간다. 이 확장기는 `wiki_graph.py --neighbors`로 이번 범위에 포함한다 (6절). 확장기가
없으면 graph를 만들어놓고 읽는 규율이 없어, 실제 조회는 매번 감으로 이뤄지고 예산은 지켜지지
않는다.

(전문 검색 인덱스 자체는 이번 범위 밖 — 진입점을 찾는 단계이며, Front Matter와 graph가 그
전제 조건을 만든다.)

## 확정된 설계 결정

| 항목 | 결정 |
|---|---|
| 기존 문서 이관 | 대화형 선별 이관. 원본은 지우지 않고 링크로 치환 |
| 코드 stale 판정 | Front Matter `sources`에 마지막 동기화 커밋 sha 기록 |
| wiki root | `docs/` — harness-init 산출물과 같은 트리 |
| `graph.yaml` 생성 주체 | `doc-sync` 스킬 전용. 커밋 훅·CI는 생성하지 않는다 |
| 검증 위치 | flow gate(layer 2)의 **runtime gate** |
| `graph.yaml` 커밋 | 커밋 대상 (edge 변화가 PR diff에 보인다) |
| Defect Memory | 이번 범위. `defect.` 접두사 판별 + `affects` edge. Rule 승격은 warn만 |

## 1. 책임 분리

| 주체 | 하는 일 | 쓰기 |
|---|---|---|
| `/wiki-init` | 대화형 선별 이관, Front Matter 부여, `wiki` 블록 기록, 최초 `graph.yaml` build | 문서 + config |
| `doc-sync` | 코드/문서 변경 반영 → Front Matter 갱신 → `graph.yaml` **build** → stale 해소 | 문서 + graph.yaml |
| `wiki_graph.py --verify` (flow gate) | **읽기 전용** 검증. drift·위반이면 exit 1 | 없음 |
| CI | graph 생성 **안 함** | 없음 |

`--verify` 실패 출력은 위반 목록과 해소 경로를 함께 낸다: `doc-sync` 스킬을 돌리거나
`python3 .claude/harness-tier/scripts/wiki_graph.py --build`.

wiki 미설치(`flow-config`에 `wiki` 없음 / `enable: false` / `root` 디렉터리 없음)이면 검증은
아무 명령도 실행하지 않고 통과한다.

## 2. 문서 스키마

wiki root 안의 `.md` 중 **`wiki_id`를 가진 파일만** wiki 노드다. Front Matter 자체는 판별자가
아니고, `id`도 아니다 — 정적 사이트 생성기(MkDocs · Docusaurus · Jekyll)의 메타데이터도 Front
Matter이며 그중 `id`는 여럿에서 문서화된 1급 필드다. 전용 키를 쓰는 이유가 그것이다
([2026-08-11 마커 분리 설계](2026-08-11-wiki-node-marker-design.md)). `wiki_id`가 없는 `.md`
(예: `docs/README.md`)는 wiki 밖이며 검증 대상이 아니다. 예외는 `wiki.index`가 가리키는 파일 —
이것은 반드시 노드여야 한다.

```yaml
---
wiki_id: auth.jwt             # 필수. ^[a-z0-9-]+(\.[a-z0-9-]+)*$ — 파일 경로와 무관한 불변 키
title: JWT                    # 필수
tags: [auth, security]        # 선택
aliases: [access token, 토큰인증]   # 선택. 전문 검색 recall 보완
related: [auth.login]         # 선택. 양방향 수동
depends_on: [auth.user]       # 선택. 단방향 수동
sources:                      # 선택. 경로 → 마지막 동기화 시점 커밋 sha
  src/auth/jwt.py: 9f3ac21
---
```

- **`used_by`는 필드가 아니다.** `depends_on`의 역 edge로 build 때 생성한다. 손으로 쓰면
  검증 에러. `depends_on`과 `used_by`를 둘 다 손으로 쓰면 SSOT가 둘이 되어 drift가 확정된다.
- **`sources`는 map 하나**로 통합한다. 리스트 + 별도 sha map은 두 필드가 어긋난다. 새 소스는
  sha를 `null`로 넣으면 `doc-sync`가 채운다.
- 링크는 항상 `id` 기준이다. 파일 rename이 링크를 깨뜨리지 않는다. `[[...]]` 위키링크는
  가독성 용도로 허용하되 검증하지 않는다.

## 3. graph.yaml과 검증 규칙

경로는 `<wiki.root>/graph/graph.yaml`. 키 정렬을 고정해 drift 비교를 결정적으로 만든다.

```yaml
# GENERATED by wiki_graph.py --build. Do not edit by hand.
version: 1
nodes:
  auth.jwt:
    path: docs/auth/jwt.md
    title: JWT
    tags: [auth, security]
    aliases: [access token]
    sources: [src/auth/jwt.py]
edges:
  depends_on: { auth.jwt: [auth.user] }
  used_by:    { auth.user: [auth.jwt] }      # derived
  related:    { auth.jwt: [auth.login] }
```

`nodes[].sources`는 **경로 리스트**다. Front Matter의 `sources`는 경로 → sha map이지만, sha는
문서 로컬 상태이지 graph 구조가 아니므로 graph에는 키만 싣는다. 이렇게 두면 sha만 갱신된
동기화가 graph drift로 오인되지 않는다.

`--verify`는 디스크의 `graph.yaml`과, Front Matter로부터 메모리에서 다시 build한 결과를
비교한다. 다르면 drift다. 비교는 **바이트가 아니라 파싱 결과**로 한다 — PyYAML emitter 는
버전마다 출력이 미묘하게 다르고, 바이트 비교는 의미가 같은 그래프를 팀원 간 왕복 block 으로
만든다.

노드 집합은 **git 인덱스**에서 온다. 파일시스템을 걸으면 gitignore된 트리(Docusaurus·MkDocs
빌드 산출물 · node_modules)와 추적되지 않는 초안까지 노드가 되고, 그러면 커밋된 graph.yaml이
재현 불가능해진다 — 다른 사람이 clone하면 그 노드가 없어 drift로 막히고, 그 사람이 다시 빌드하면
원저자가 막힌다. 즉 **`git add`가 문서를 위키에 넣는 행위**이며, 새 문서는 스테이징한 뒤에
build해야 한다. git이 답할 수 없으면(저장소 아님) 파일시스템 순회로 폴백한다. 저장소 **안**에서
git이 일시적으로 답하지 못하면 폴백 집합을 신뢰할 수 없으므로 `--build`는 쓰기를 거부하고
(재실행 안내), `--verify`는 fail-open 한다.

노드 판별자는 `wiki_id`다. `---` 블록이 있어도 `wiki_id`가 없으면 노드가 아니며 검증 대상이
아니다 — 전용 키를 쓰는 이유는 2절과 같다. 예외는 `related` · `depends_on` · `affects` ·
`sources` 같은 wiki 전용 필드가 있는데 `wiki_id`만 빠진 경우다: 이때만 경고한다(3건 + 건수) —
wiki에 들어올 뜻은 있는데 마커만 빠졌다는 신호이기 때문이다. 그런 필드조차 없으면 그 문서는
wiki와 무관하다고 보고 조용히 넘어간다.

`--verify` 판정:

| 위반 | 결과 |
|---|---|
| `wiki_id` 중복 · `wiki_id` 형식 위반 · `title` 누락 | block (exit 1) |
| front matter 가 열리고 닫히는데 파싱에 실패했고, 그 원문에 `wiki_id:` 줄이 있음 | block |
| front matter 가 열리고 닫히는데 파싱에 실패했고, 그 원문에 `wiki_id:` 줄이 없음 | warn, exit 0 |
| dangling reference (없는 id 참조) | block |
| `depends_on` 순환 | block |
| `used_by`를 손으로 작성 | block |
| `sources` 경로가 실존하지 않음 | **warn** — 생성물·gitignore·타 브랜치 파일이 정당하게 있다 |
| `title`·sha 등 텍스트 필드가 YAML 1.1 로 int/bool 이 됨 | block (따옴표 안내) |
| `graph.yaml`이 Front Matter와 불일치 (drift) | block |
| orphan (`wiki.index`에서 도달 불가) | warn, exit 0 |
| `wiki.index` 경로에 대응하는 wiki 노드가 없음 (orphan 검사 자체를 생략) | warn, exit 0 |
| 파일 줄 수 > `wiki.max_lines` (기본 400, `0`=off) | warn, exit 0 |
| Front Matter 는 있는데 wiki 전용 필드만 있고 `wiki_id` 가 없음 (= 마커 누락) | warn, exit 0 |

경고는 종류마다 3건 + 건수로 자른다. 매 커밋에 찍히고, 다른 이유로 block될 때는 하나의 deny
사유에 통째로 실리기 때문이다.

도달 가능성은 **graph edge 기준**이다 — `wiki.index` 노드에서 `related` · `depends_on` ·
`used_by`를 방향 무시하고 따라간다. 본문의 markdown 링크는 세지 않는다.

**코드 stale은 검증이 판정하지 않는다.** 소스별 `git log`가 문서 수만큼 필요해 커밋마다
비싸고, 검증을 읽기 전용·구조 전용으로 유지하는 편이 1절의 책임 분리와 맞다. stale은
`doc-sync`가 담당한다.

## 4. 검증을 runtime gate로 등록

`flow-tiers.yaml`의 네 티어 전부에 `wiki`를 추가한다. 아래는 `gates` 키만 발췌한 것이며,
각 티어의 `description` · `superpowers` 키와 파일의 `merge_strategy` 절은 그대로 둔다.

```yaml
tiers:
  docs:    { gates: [doc-sync, wiki] }
  dev:     { gates: [precommit, review, doc-sync, wiki] }
  staging: { gates: [precommit, review, security-scan, bump, wiki] }
  release: { gates: [precommit, review, security-scan, security, wiki] }
```

`scripts/_harness_paths.py`의 `RUNTIME_GATES`를 `("precommit", "security-scan", "wiki")`로
확장한다. 이것으로 `missing_gates`가 `wiki.done` 마커를 요구하지 않게 된다 — 마커가 아니라
훅이 실제로 스크립트를 실행하는 게이트다.

실행은 **모듈 사전검사 통로가 아니라 전용 스텝**이다. `precommit-runner.sh`가
`flow_gate_check.py --wiki-check`를 flow gate 바로 다음에 부르고, merge check·flow gate와
같은 `exit 2 전용` 계약을 쓴다.

처음에는 `--module-commands`에 명령 하나를 얹어 셸을 안 고치는 쪽으로 갔지만, 두 통로의 오류
계약이 반대라서 그럴 수 없었다. 모듈 통로는 **0 이 아닌 모든 종료를 "검사 실패"로 읽는다** —
스크립트 유실·인터프리터 오류·OOM 처럼 판정이 아닌 실패까지 저장소 전체의 커밋을 막게 되고,
wiki 는 Invariant #1 의 세 fail-closed 예외 중 어느 것도 아니다. 부수적으로 두 가지가 더 따라
왔다: 모듈 통로는 출력을 **실패할 때만 출력되는 로그**로 모으므로 graph 품질 경고(orphan ·
max_lines · defect→rule)가 사람에게 영영 닿지 않았고, 차단 사유가 `모듈 사전검사 실패:
<명령 문자열>` 이라는 엉뚱한 이름으로 나왔다.

```python
# gates 에 "wiki" 가 있고 flow-config.wiki 가 살아있을 때만, 같은 프로세스 안에서
wiki_gate(root, gates)  # True = block → sys.exit(BLOCK_EXIT_CODE)
```

명령 문자열이 아니라 in-process 호출이라, `sys.executable` 을 문자열에 굳혀 넣는 문제(그 인터
프리터가 나중에 셸이 실행할 때도 있으리라는 보장이 없다)와 Windows 경로의 셸 토큰화 문제가
통째로 사라진다. `flow_init_setup.py`의 `COPY_FILES`에 `scripts/wiki_graph.py`를 추가해 호스트
쪽 sibling import 를 채운다.

**출력은 전부 stdout이다.** 두 이유 모두 훅 계약에서 온다.

- `python3 <없는 파일>` 자체가 stderr에 불평하며 **exit 2**로 죽는다 — block과 똑같은 모양이다.
  runner가 stderr를 읽으면 스크립트 복사가 반쯤 실패한 호스트가 인터프리터 오류를 사유로 모든
  커밋을 막게 된다. 인터프리터는 stdout에 쓰지 않으므로 stdout만 읽으면 이 충돌이 없다.
- exit 0에서는 훅의 stdout과 stderr **둘 다 디버그 로그로만** 간다. 통과한 커밋에서 품질 경고를
  사람에게 보여주는 유일한 문서화된 통로는 공용 JSON 필드 `systemMessage`("warning message shown
  to the user")다. 그래서 exit 0이면 `{"systemMessage": ...}`를 stdout으로 내고, runner가 커밋을
  허용하는 시점에 그대로 흘려보낸다.

pre-commit 훅, `OWNED_HOOK_ID`, `pre-commit-hooks.example.yaml`은 수정하지 않는다.

### 검증 위치를 pre-commit이 아닌 flow gate로 정한 이유

- **pre-commit local 훅**은 터미널·CI 커밋까지 커버하지만, `COPY_FILES`·`OWNED_HOOK_IDS`
  확장과 example yaml 수정이 따르고, wiki를 쓰지 않는 프로젝트의 설정 파일에도 훅이 붙는다.
- **`flow-config.modules[].checks` 커스텀 체크**는 새 메커니즘이 필요 없지만, 호스트가 손으로
  등록해야 하고 지우면 검증이 사라지며, 해당 모듈 경로가 변경된 커밋에서만 발동한다.
  (예: 소스 파일을 지웠는데 그것을 `sources`로 참조하는 노드가 남는 경우를 못 잡는다.)
- **runtime gate**는 정책(plugin-owned `flow-tiers.yaml`)이 소유하므로 호스트가 끌 수 없고,
  `wiki` 블록만 있으면 자동으로 발동하며, 마커가 아니라 실제 실행이다.

### 알려진 실패 모드 — 터미널 커밋의 지연 탐지

layer 2 게이트이므로 **Claude 세션 커밋만** 커버한다. 터미널 커밋은 검증되지 않는다. 이는 다른
runtime gate와 동일한 한계지만, graph는 생성물이라 결과가 눈에 띄게 다르므로 명시한다.

```
터미널에서 문서 수정 후 커밋
  → graph.yaml 이 조용히 낡음 (아무도 막지 않음)
  → 다음 Claude 세션 커밋에서 --verify 가 drift 로 차단
  → doc-sync 한 번으로 해소
```

**탐지는 지연되지만 유실되지는 않는다.** graph가 영원히 썩는 시나리오는 없다 — 다음 세션
커밋이 반드시 걸린다.

두 가지 부수 조건이 따라온다.

- **검사 대상은 working tree다.** 훅은 PreToolUse 라 `git commit` 이 스테이징하기 전에
  돈다 — 검사할 "커밋된 상태"가 아직 없다. 따라서 `graph.yaml` 은 그것을 만들어낸 문서와
  **함께 스테이징**되어야 한다. 다시 빌드해 놓고 문서만 스테이징하면 게이트는 통과하는데
  커밋에는 새 Front Matter 옆에 낡은 graph 가 들어간다 (역시 다음 세션 커밋에서 걸린다).
- **promotion 에는 graph 를 다시 만드는 게이트가 없다.** `doc-sync` 는 promotion 게이트가
  아니므로, 터미널 커밋으로 들어온 drift 는 승격 커밋이 막히는 형태로 나타난다. 해소는
  `--build` 를 돌려 그 커밋에 포함시키는 것이다.

대가는 **차단당하는 사람과 원인을 만든 사람이 다를 수 있다**는 것이다. 위키를 건드리지도 않은
사람이 무관한 커밋을 하려다 남이 만든 drift로 막힌다. 해소는 `doc-sync` 한 번이라 무겁지
않지만, 이것을 버그로 오해하지 않도록 `--verify` 실패 메시지에 **누가 언제 만든 drift인지**를
같이 낸다: drift가 난 노드의 파일 경로와 그 파일의 마지막 커밋(`git log -1`)을 함께 출력한다.

이 지연 탐지가 실무에서 마찰이 되면 pre-commit local 훅(같은 `--verify` 재사용)을 추가하는
것이 다음 수순이다. 스크립트는 이미 그 형태이므로 등록만 남는다.

## 5. flow-config.wiki 블록

```yaml
wiki:
  enable: true
  root: docs/              # wiki root. harness-init 산출물과 같은 트리
  index: docs/index.md     # graph 진입점 (orphan 판정 기준)
  max_lines: 400           # 한 파일 한 개념 lint. 0 = off
  context_lines: 2000      # --neighbors 기본 예산 (줄). ≈20k 토큰
  defect_rule_threshold: 3 # 같은 tag 로 N 번 터지면 Rule 승격 warn. 0 = off
```

`context_lines`의 단위가 토큰이 아니라 **줄**인 이유: 게이트 스크립트는 PyYAML 외에 의존을
두지 않으므로 토크나이저가 없다. 줄 수는 의존 없이 정확히 세지고, `max_lines`와 단위가
통일된다. 환산은 대략 1줄 ≈ 10토큰이다.

`doc_sync.dirs`가 이미 `docs/`를 포함하므로 별도 조율 없이 겹친다.

## 6. wiki_graph.py CLI와 doc-sync 확장

```bash
python3 wiki_graph.py --build     # Front Matter → graph.yaml 쓰기.  doc-sync 전용
python3 wiki_graph.py --verify    # 읽기 전용. 위반/drift 시 exit 1. flow gate 전용
python3 wiki_graph.py --stale     # sources sha vs git log → JSON. 항상 exit 0. doc-sync 소비
python3 wiki_graph.py --neighbors <id> [--budget N]   # 예산 내 이웃 문서 경로. 없는 id 는 exit 1
```

의존은 PyYAML만 사용한다(게이트 스크립트의 기존 의존과 동일). Invariant 2에 따라
`PYTHONUTF8=1` · `force_utf8_io()` · `encoding="utf-8"` 방어를 유지한다.

### --neighbors

진입점 `id`에서 BFS로 넓히며 파일 경로를 모으고, 누적 줄 수가 예산(`--budget`, 생략 시
`wiki.context_lines`)에 닿으면 멈춘다. 출력은 경로 목록(한 줄에 하나) + 마지막 줄에 누적
줄 수와 잘린 노드 수 요약.

- **edge 우선순위**: 같은 hop 안에서 `depends_on` → `used_by` → `affects`/`defects` →
  `related` 순. 구조적 의존이 먼저 예산을 차지하고, 느슨하고 수가 많은 `related`가 마지막이다
  (`affects`/`defects`는 7절)
- **순환**: visited 집합으로 처리한다. 깊이 제한은 두지 않는다 — 예산이 유일한 제동이다
- **진입점 자신은 항상 포함**한다. 진입점 하나가 이미 예산을 넘겨도 그것만은 낸다 (빈 결과
  방지)
- **없는 id**: stderr에 경고, **exit 1**, 빈 출력. exit 0 + 빈 출력은 "이웃 없음"과 구별이
  안 돼 호출자(doc-sync)가 조회 실패를 "조화할 것 없음"으로 읽고 지나간다
- **wiki 미설치**: `--verify`와 같이 아무 출력 없이 exit 0

`--build`/`--verify`와 달리 게이트가 부르지 않는다. 조회용이므로 exit 1이 커밋을 막을 일은
없다.

`doc-sync`에 **Mode W**를 추가한다 (기존 Mode A → Mode B 뒤. wiki 미설치면 통째 skip):

1. `--stale` 실행 → 변경된 코드가 걸린 노드 목록 확보
2. 각 노드에 `--neighbors`를 돌려 **조화(harmonize) 대상 이웃**을 좁힌다. Mode B는 지금
   `**/*.md`를 키워드로 grep해 관련도 점수로 고르는데, wiki가 있으면 graph가 그 관계를 이미
   들고 있으므로 추정 대신 조회다. 그 뒤 Mode A가 고친 문서와 대조해 본문 갱신
3. **본문을 실제로 손댄 노드만** `sources[path]` sha를 현재 값으로 갱신. 고치지 않은 stale은
   갱신하지 않고 리포트에 남긴다 (도장 찍기 방지 — `/flow` Critical rule 1과 같은 규율)
4. wiki root 안에 Front Matter 없는 신규 `.md`가 생겼으면 부여
5. `--build` → `graph.yaml` 재생성
6. `--verify` 통과 확인 후 기존 `doc-sync.done` 마커

`doc-sync` frontmatter `allowed-tools`에 3줄을 추가한다. 경로 glob 없이 정확히 열거한다
(`.claude/rules/skill-frontmatter.md` 규율):

```
Bash(python3 .claude/harness-tier/scripts/wiki_graph.py --build)
Bash(python3 .claude/harness-tier/scripts/wiki_graph.py --verify)
Bash(python3 .claude/harness-tier/scripts/wiki_graph.py --stale)
```

`--neighbors`는 **넣지 않는다.** 인자로 임의의 `id`를 받으므로 유한 집합으로 열거할 수 없고,
`--neighbors *` 같은 규칙은 스크립트 경로 뒤를 전부 여는 셈이라 열거 규율을 깬다. 매번
프롬프트가 뜨지만, 조회는 노드당 한 번이므로 `--build`/`--verify`처럼 매 실행 반복되지 않는다.

## 7. Defect Memory

장애 기록은 장기 메모리가 아니라 **실패 사례 데이터베이스**다. `Input → Output → Defect →
Root Cause → Fix`를 본문에 적고, 기계가 읽을 부분만 Front Matter로 뺀다. 목적은 보관이 아니라
Prompt 개선 · Rule 추가 · Regression Test 생성으로 이어지는 것이다.

**판별자는 `wiki_id` 접두사다** — `wiki_id`가 `defect.`로 시작하면 defect 노드다. 위치는
`<wiki.root>/defects/<slug>.md`.

```yaml
---
wiki_id: defect.jwt-clock-skew # defect. 접두사가 판별자
title: JWT 만료 검사가 clock skew 를 못 견딤
tags: [auth, expiry]          # Rule 승격 카운트의 묶음 키
affects: [auth.jwt]           # 필수. 영향받은 wiki 노드 id
commit: 66b7463               # 선택. 원인 커밋 sha
regression_test: tests/test_jwt.py::test_clock_skew   # 선택
promoted_to_rule: rules/jwt-expiry.md                 # 선택. 승격됐다면 그 rule 경로
---
```

`affects`는 새 edge 종류이고, 역 edge `defects`가 build 때 생성된다 — `used_by`와 같은
관계다. 이것으로 "이 문서와 얽힌 장애 이력"이 조회 가능해진다. `defects`를 손으로 쓰면
`used_by`와 마찬가지로 검증 에러다.

`--verify` 판정 추가분:

| 위반 | 결과 |
|---|---|
| defect 노드에 `affects` 없음 | block |
| `affects`가 없는 id를 가리킴 | block (기존 dangling 규칙) |
| `defects`를 손으로 작성 | block |
| `commit`이 hex 7~40자가 아님 | block |
| `regression_test`·`promoted_to_rule`의 파일이 실존하지 않음 | block |
| defect가 아닌 노드가 위 필드를 사용 | block |
| 같은 `tags` 묶음의 defect가 `wiki.defect_rule_threshold` 이상인데 `promoted_to_rule`이 하나도 없음 | warn, exit 0 |

`commit`은 sha **형식**만 본다. 실존 여부를 보려면 `git cat-file`이 필요한데, 그것은 검증을
읽기 전용·구조 전용으로 두는 3절 원칙을 깬다. `regression_test`는 `::` 앞의 파일 경로만
검사한다.

**Rule 승격은 자동화하지 않는다.** 임계값(`wiki.defect_rule_threshold`, 기본 3)은 warn만
낸다 — "이 태그로 3번 터졌는데 아직 Rule이 없다"는 신호다. 무엇을 Rule로 올릴지는 사람이
정한다. 1회 재발마다 Rule을 만들면 rule set이 노이즈가 된다.

`--neighbors`의 edge 우선순위에서 `affects`/`defects`는 `used_by` 다음, `related` 앞이다.
장애 이력은 특정 노드에 대한 강한 사실이고 수가 적은 반면, `related`는 느슨하고 많다.

`/wiki-init`과 `doc-sync`는 defect 문서를 위 5단 본문 구조로 생성한다.

## 8. /wiki-init 스킬

frontmatter는 `disable-model-invocation: true` — 설치형 wizard이므로 `/flow-init` ·
`/harness-init` · `/harness-deployments`와 같은 부류다. 따라서 `evals/cases.yaml` 항목은
없다(모델이 부르는 스킬만 측정한다).

전제: `flow-config.yaml` 존재. 없으면 `/flow-init`을 먼저 실행하라고 안내하고 중단한다
(`harness-deployments`와 동일 패턴).

1. **root 확인** — 기본 `docs/`. `AskUserQuestion`으로 확정
2. **스캔** — root 밑 `.md`별로 줄 수 · H2 개수 · Front Matter 유무를 집계해 분리 후보 표 제시
3. **선별** — 사용자가 이관할 문서를 고른다. 후보가 많으면 배치로 나눠 묻는다
4. **분리** — H2 단위로 개념을 추출해 새 파일로 만든다. 원본에는 링크만 남기고 지우지 않는다
5. **Front Matter 부여** — `wiki_id`는 경로에서 기계적으로 도출(`docs/code-style/python.md` →
   `code-style.python`). `related`/`depends_on`은 LLM이 기존 문서를 읽고 **추천**하고 사람이
   확인한 뒤 확정한다
6. **index 생성/갱신** — 모든 노드를 링크한다 (orphan 방지)
7. **`flow-config.wiki` 블록 upsert** — 마커 블록만 교체하고 나머지는 보존한다
   (harness-rules 2 "No overwriting")
8. `--build` → `graph.yaml`
9. `--verify` 통과 확인. 실패하면 고치고 재시도
10. **커밋하지 않는다** — `/flow`의 책임 (harness-rules 3)

재실행은 증분이다. 이미 `wiki_id`가 있는 문서는 건드리지 않는다.

## 9. harness-init 연동

**harness-init은 wiki 설치 여부와 무관하게 항상 Front Matter를 붙인다.** 설치 순서 의존을
없애는 것이 핵심이다 — `harness-init`이 먼저든 `/wiki-init`이 먼저든 결과가 같다. wiki
미설치 프로젝트에서 Front Matter는 무해한 메타데이터이고, 나중에 `/wiki-init`을 실행하면 그
순간 전부 노드가 된다.

- `rules/harness-rules.md`에 **8-2를 신설**한다: 기술문서는 wiki 노드 형식으로 저작 —
  Front Matter 필수, 한 파일 한 개념, `sources`에 근거 코드 경로 기재. rule 7(SSOT)의
  문서판 강제다
- `skills/harness-authoring/templates/`의 문서 템플릿에 Front Matter 블록을 추가한다:
  `srs` · `sds` · `code-style` · `onboarding` · `docs-readme`. **`rule`은 제외한다** — rule
  frontmatter 는 선택적 `paths` 하나만 허용되고, 스킬은 알 수 없는 키에 hard-error 를 낸다.
  공식 문서가 rule 의 unknown-key 허용을 명시하지 않으므로 추측으로 실을 수 없다
- `wiki_id` 네임스페이스는 폴더 기반 기계 변환이다 — `docs/sds/api.md` → `sds.api`. 사람이 짓지
  않으므로 충돌하지 않는다. 템플릿의 `{{ID}}` 도 하드코딩 슬러그가 아니라 이 규칙으로 채운다
  (템플릿마다 자기 출력 경로 예시를 주석으로 들고 있다)
- `docs/README.md`는 사람용 랜딩이면서 동시에 노드다 (`wiki_id: readme`). `docs/index.md`가 graph
  진입점이며, 둘의 `wiki_id`가 겹치지 않도록 README 쪽을 `readme`로 둔다

## 범위 밖

- 전문 검색 인덱스(SQLite FTS5/BM25) 구축 — 진입점을 찾는 단계다. 진입점이 정해진 뒤의
  확장은 `--neighbors`가 이번 범위에서 담당한다
- Rule 승격 **자동화** — 임계값 warn까지만 낸다. 무엇을 Rule로 올릴지는 사람이 정한다 (7절)
- Prompt 개선 루프 자동화 — defect가 Prompt/Rule 개선으로 이어지는 것은 사람의 판단이다.
  이번 범위는 그 판단에 필요한 기록과 신호까지다
- 기존 문서의 전체 자동 이관 — 대화형 선별만 지원한다
- 터미널 커밋에 대한 graph 검증 — 실패 모드는 4절에 명시했다. 다음 수순은 같은 `--verify`를
  재사용하는 pre-commit local 훅이다
